# Orbital Rift — «Живой космос»

Версия: 1.0 · 7 сентября 2026 · Статус: дизайн и техническое ТЗ, не реализовано.

Обновление 8 сентября: реализованы ограниченные M1/M2, правила и Canvas/checkpoint M3/M4, карта с развилками M5; точное состояние и ограничения — в [LIVING_COSMOS_PROGRESS.md](LIVING_COSMOS_PROGRESS.md). Остальной документ описывает целевую систему, не готовые возможности.

Документ предназначен агенту, который будет реализовывать систему в существующем проекте. Все новые численные значения ниже — стартовые настройки для тестирования, а не доказанный баланс. Существующий код и настройки пользователя нельзя заменять целиком этим документом.

## 1. Решение в одном абзаце

Превратить последовательность боёв в путешествие через узнаваемые области космоса. У каждой области есть собственная атмосфера и одно понятное правило, которое взаимодействует с уже существующими кораблями, ядром, сцепкой и атаками. Между боями игрок выбирает маршрут на горизонтальной карте, иногда — рискованный проход через кротовую нору. Быстро завершённый бой повышает шанс временного усиления следующего боя. Пространство меняется во время уже существующего светового прыжка; в бою оно остаётся читаемым и не конкурирует с противниками.

### Обязательные продуктовые принципы

1. **Понятная причина результата.** Игрок понимает, что его ударило, что изменилось в пространстве и откуда получен баф.
2. **Не только новая окраска.** Значимая смена региона меняет хотя бы одно взаимодействие, но цвет сам по себе не является правилом.
3. **Не усложнять управление.** Никаких дополнительных постоянно видимых боевых кнопок. Выборы — между боями.
4. **Дать истории для двоих.** «Ты отправил ядро в нору, а оно вышло за боссом» лучше очередного невидимого +5%.
5. **Сохранять поле видимым.** HUD, карта, названия и уведомления не перекрывают ни верх, ни низ полной текущей траектории.
6. **Скорость — возможность, не наказание.** Медленный игрок получает обычную награду, не теряет HP/MMR из-за таймера и может пройти забег без темпо-бафов.
7. **Музыка не управляет правилами.** BPM, громкость, микрофон и качество графики меняют только представление. Два клиента могут слушать разную музыку без различий в бою.

### Что не входит в эту инициативу

- Открытый мир со свободным полётом, смена управления, dedicated servers, host migration.
- Новая постоянная валюта, монетизация, новая формула MMR, полный редизайн всех экранов.
- Переписывание GameManager целиком, обновление Unity/сетевых пакетов «заодно».
- Возвращение взаимодействия белых звёзд с музыкальными кольцами: оно было отменено пользователем.
- Созвездия, новые разрывы/срезы колец, постоянно видимая пунктирная орбита.

## 3. Границы первой версии и дальнейшего релиза

### Вертикальный срез V0: доказать, что играть интересно

- Только отдельный экспериментальный **Solo Expedition: Живой космос**, явно «без рейтинга».
- Один законченный маршрут на 5–7 посещений, одна настоящая развилка, два визуальных пространства.
- Один интерактивный объект: парные линзы, через которые проходят ядро и снаряды.
- Темпо-награда с тремя типами модулей и защитой от невезения.
- Настоящий выбор на Canvas-карте; сохранение комнаты и награды; повторяемый seed.
- Все правила пишутся сразу общими, но сложный сетевой rollout не блокирует первое игровое тестирование.

### V1: полная экспедиция

- Одиночная и кооперативная экспедиции на одном наборе правил.
- Три пространства с механикой; два дополнительных визуальных профиля можно выпустить позже.
- Настоящие развилки, опциональные кротовые норы, общая фазовая модель, кооп-магазин и выбор наград.
- Пример полного маршрута: 14 глубин, не более 24 узлов с альтернативами; примерно 7–9 боёв в зависимости от выбора.
- Желаемая длительность 8–12 минут — гипотеза, проверяется плейтестом, а не искусственным растягиванием волн.

### V1.1: перенос атмосферы в другие режимы

| Режим | Когда меняется пространство | Карта | Новые правила и темпо-бафы |
| --- | --- | --- | --- |
| Solo Expedition | При переходе в другую область | Полный выбор пути между боями | Вся система после V0 |
| Co-op Expedition | Тот же переход, решённый хостом | Общая карта и голосование | Те же правила, командная награда |
| Classic | Существенная смена после босса; малые вариации каждые 3 фазы | Только лента пройденных областей на паузе | Сначала только визуал; механики отдельным opt-in ruleset |
| Defense | После пачки из 3 волн, крупная смена после элиты/босса, если такой milestone реально есть | Маршрут конвоя между пачками, без выбора в первой версии | Сначала визуал; опасности не должны появляться внутри корпуса флагмана |

Не придумывать несуществующий event для защиты: если отдельного босса нет, адаптер использует завершение пачки волн. Обычные classic-волны не замедляют звёзды как бой с боссом. Ручные настройки яркости/радиусов/ореолов пользователя сохраняются.

## 4. Игровой цикл и фазовая модель

```text
Вход в область → Прибытие/показ угрозы → Бой → Зачистка → Награда
                                                           ↓
Следующая область ← Прыжок ← Подтверждение маршрута ← Карта/магазин
```

Единый `EncounterPhase`:

| Фаза | Можно двигаться/стрелять | Урон | Счётчик темпа |
| --- | --- | --- | --- |
| Arrival | Полёт по сценарию; боевой ввод не расходуется | Ни игрокам, ни врагам | Не идёт |
| Combat | Обычное управление | По видимым атакам/правилам | Идёт по правилам раздела 7 |
| Clear | Движение допустимо; новых атак нет | Нет; уничтожить/обезвредить оставшиеся опасности | Зафиксирован |
| Reward | UI выбора | Нет | Зафиксирован |
| RouteChoice | UI карты | Нет | Не идёт |
| Docking / Shop | Существующая стыковка / UI | Нет | Не идёт |
| Departing | Световой прыжок | Нет | Не идёт |
| Completed / Failed | Результат | Нет | Зафиксирован |

- Пауза — отдельное состояние поверх фазы, не новый вид комнаты.
- Порядок при завершении боя: зафиксировать clear один раз → остановить урон → вычислить награду → сохранить → показать UI.
- Звёзды начинают разгон после победы. Пик светового прыжка и смешивание двух регионов выполняются в `Departing`, после подтверждения маршрута. Это уточняет текущий автопрыжок: он не должен завершиться до того, как игрок выбрал, куда лететь.
- Один владелец перехода управляет звездным потоком, туманностью и музыковизуалом. Старый детектор `wasSpaceCombat` не должен одновременно запускать второй прыжок.
- Использовать текущую длительность прыжка из StarStreamSettings как начальную. Входную защиту 3.4 с не сокращать без отдельного теста видимости босса.
- Во время магазина сначала показать имеющуюся анимацию стыковки, затем открыть карточки. Не телепортировать корабль сразу в окно магазина.
- Провал имеет приоритет над clear, если последнее HP команды потеряно в том же authoritative tick, что и последний враг. Не выдавать награду за такой бой. Покрыть отдельным тестом.

## 5. Области космоса

### 5.1 Разделить внешний вид и физику

`SpaceVisualProfile` — палитра, плотность/масштаб туманности, свет, глубина, профиль прыжка.

`SpaceRuleDefinition` — реальная механика, параметры опасностей, совместимости, описание.

`SpaceRegionDefinition` — сочетание профиля и допустимых правил, выбранное генератором.

Можно сначала выпустить визуальный профиль без механики, но в UI тогда писать только название области, не обещать несуществующий эффект. Нельзя привязать урон к цвету пикселей шейдера.

### 5.2 Три основных области V1

| Область | Узнаваемый вид | Одно главное правило | Как использовать вдвоём |
| --- | --- | --- | --- |
| Синий предел | Глубокий синий, холодные разреженные слои, небольшие звёзды | Парные гравитационные линзы перенаправляют ядро и снаряды | Отправить ядро через линзу за спину угрозе; союзник ловит обратку |
| Янтарный фронт | Янтарно-медные облака по периферии, медленный внутренний свет | Заряженные облака можно разрядить попаданиями в видимый узел | Один заряжает, второй подталкивает ядро/врага в зону разряда |
| Обломки ковчега | Сланцево-серый, приглушённый зелёный свет, большие медленные силуэты | Один подвижный отражатель меняет направление снарядов | Кинетикой повернуть отражатель так, чтобы атака босса вернулась к нему |

### 5.3 Точные правила интерактивных объектов

**Парные линзы — первый объект для реализации.**

- Пара дисков с входным/выходным указателем; цветом не ограничиваться, направления показывать формой.
- Не телепортируют корабли в V1: сохраняем предсказуемую траекторию и управление.
- Ядро, обычные player shots и обычные enemy bolts проходят; cleave, круговые волны, сцепка и декорации не проходят.
- Выход: `exitCenter + exitNormal * (exitRadius + objectRadius + epsilon)`; скорость поворачивается на разницу ориентаций, модуль скорости, элемент, владелец и оставшееся время жизни сохраняются. Урон не умножается.
- Одна сущность может пройти не более 2 раз за жизнь снаряда; ядро — снова не раньше 0.8 с. При достижении лимита снаряд пролетает через линзу без телепортации, не исчезает.
- Пара располагается внутри игровой области, вне ядра появления угрозы, вне стыковки и вне дистанции `радиус корабля + 0.5 world units` от текущей траектории. Это стартовый зазор; геометрический валидатор проверяет его на всех формах.
- Линзы неподвижны в течение боя V1. Они не возникают внезапно под снарядом или пилотом.
- Выходящий вражеский снаряд не может появиться в пределах 0.6 с расчётного подлёта к кораблю; при небезопасном выходе использовать другой валидный вариант пары или отказаться от пары до начала боя.
- Все перемещения и попадания решает авторитетная симуляция; визуальный штрих между линзами не является хитбоксом.

**Разрядный узел — второй объект.**

- Один узел, шкала из 3 сегментов, радиус зоны воздействия 0.8 world units как стартовая настройка.
- Каждый валидный контакт снаряда добавляет 1 заряд, общий cooldown контактов 0.25 с. Не учитывать один снаряд многократно.
- На 3 зарядах: 0.9 с видимого предупреждения → разряд → 3 с восстановления. Все стороны видят заполнение и область поражения.
- Разряд толкает ядро наружу и наносит 2 базовых урона врагу / не более 1 HP команде через единый канал урона. В первой учебной комнате игрокам урон отключён и это указано в описании.
- Случайные музыкальные молнии никогда не заряжают узел и не наносят урон.
- Сцепка пересекает узел: +1 заряд с cooldown 1 с, без отдельного бонусного умножения. Тем самым друг может ускорить разряд раньше ожидаемого.
- Нет неограниченной цепи «взрыв зарядил себя»: разряд не заряжает свой узел; в V1 узел один.

**Отражатель — третий объект.**

- Одна короткая видимая панель, не перекрывающая корабельную траекторию. Кинетическое попадание поворачивает её на 15°, cooldown 0.3 с.
- Обычные снаряды отражаются геометрически от нормали. Не отражать cleave/кольцевую волну/сцепку.
- Максимум один рикошет на снаряд; второй контакт поглощает снаряд с тихим коротким эффектом.
- Отражённая вражеская пуля может повредить врага, но не выдаёт отдельную награду сверх обычного убийства. Принадлежность урона фиксируется в событии.
- Панель не должна полностью блокировать единственный путь попадания по боссу. Проверить доступность атаки для обоих лепестков восьмёрки.

### 5.4 Дополнительные визуальные профили, после V1

- **Фиолетовый разлом:** мягкие протяжённые полосы и далёкие плазменные оболочки. Хороший профиль для кротовой норы, без постоянной тряски.
- **Тихая бездна:** почти чёрный фон, редкие синие звёзды, большие медленные тени. Комната передышки — контраст после яркого боя.

Не вводить сразу пять разных наборов опасностей. Сначала проверить три взаимодействующих объекта.

### 5.5 Ограничения генератора сочетаний

- V0/V1: максимум одно активное правило пространства и один дополнительный интерактивный объект в бою.
- Первый новый объект показывается без элиты и без второго незнакомого правила.
- Не совмещать зеркало первого босса с новым разрядным узлом в первом релизе: слишком много конкурирующих сигналов.
- Не менять направление управления и скорость корабля скрытым свойством области.
- Правила размещения учитывают весь morph и поворот текущей траектории, а не только начальный круг.
- При невалидном размещении использовать заранее проверенную безопасную конфигурацию; не пытаться бесконечно регенерировать во время кадра.

## 6. Горизонтальная карта и кротовые норы

### 6.1 Карта должна представлять реальный маршрут

- Слева старт, справа цель; 2–3 доступных альтернативы в точках выбора. Пройденный путь подсвечен, недоступный погашен.
- Видны тип комнаты, область, обычный/повышенный риск, гарантированная награда и известное правило. Никаких ложных вероятностей.
- Разные регионы — широкие фоновые полосы карты с названиями; это не новые панели поверх боевого поля.
- На маленьком экране полная карта горизонтально прокручивается и автоматически центрирует текущий узел. Не уменьшать весь граф до нечитаемых точек.
- В бою остаётся только компактная существующая цепочка прогресса. Полная карта открывается между боями или на паузе.
- Текущая и следующая комната сохраняют одинаковую типографику, размер и Y-положение. До выбора писать справа «ДАЛЕЕ: ВЫБОР ПУТИ», а не угадывать соседний индекс.
- Счётчик: «ПРОЙДЕНО 4 · ДО ЦЕЛИ 3–5», если ветки разной длины; не рисовать неверное `4/14` по общему числу всех альтернатив.

### 6.2 Новый граф

- Ввести отдельную версию генератора. Старые сохранённые забеги не переводить на новую геометрию автоматически.
- Directed acyclic graph: обычное ребро всегда ведёт к большей `Depth`. ID не равен глубине и не означает порядок посещения.
- `CurrentNodeId`, `VisitedNodeIds`, `AvailableNextNodeIds`, `CommittedNextNodeId` — явное состояние.
- Выход только по существующему доступному ребру из текущего узла. Повторное посещение пройденного узла в V1 запрещено.
- Минимум один гарантированный старт→босс→выход путь; ни одна ветка не обходит финального босса.
- До обязательной элиты/финального босса на каждом возможном пути есть доступ к сервисной комнате. Область не меняет цвета случайно после каждой маленькой волны; изменения объединены в регионы.
- В V1 максимум 24 узла. Увеличение лимита — отдельное изменение после профилирования и UI-проверки.

Пример глубин полного маршрута, альтернативы добавляются внутри глубины:

```text
0 Старт
1 Бой → 2 Выбор: бой / событие → 3 Магазин → 4 Элита
5 Переход области
6 Бой → 7 Выбор: элита / обычный бой → 8 Магазин → 9 Элита
10 Переход области → 11 Бой → 12 Финальный босс → 13 Выход
```

Указанные переходы областей не обязаны быть отдельным старым `SectorRoomType`. Предпочтительно ввести `RouteNodeKind`/тип ребра, сохранив численные значения существующего enum для сетевой совместимости. Магазин/выход/переход не должны требовать «убить фиктивного врага с HP».

### 6.3 Кротовая нора как выбор маршрута

Это НЕ парная линза внутри боя. Два разных объекта с разными названиями в коде: `WormholeEdge` и `PairedLens`.

- Нора — заранее видимое альтернативное ребро, которое пропускает ровно одну обычную боевую комнату и ведёт к более сложному варианту следующего боя.
- Нельзя пропустить магазин перед обязательным боссом, финального босса, tutorial нового правила или сразу две комнаты.
- Игрок заранее видит: «Пропустить бой • следующий бой: элита • награда элиты». Это существующая усиленная встреча, не скрытый множитель всех характеристик.
- Пропущенный бой не выдаёт score, темпо-бросок, магазинную награду или отметку прохождения.
- Для V0 нору можно оставить только как обязательный красивый переход региона; **не показывать выбор**, пока реальная альтернативная логика не готова.
- В анимации: сжатие фоновых слоёв → вытянутые цвета → проявление нового профиля. UI не искривлять этим переходом; эффект зеркала босса остаётся отдельной механикой.

### 6.4 Выбор для двоих

- Хост авторитетен, но не выбирает за обоих молча. Оба клиента присылают голос `NodeId` и видят два маркера.
- Совпали подтверждённые голоса — зафиксировать путь. Один может менять голос до фиксации.
- После первого подтверждения начинается видимый таймер 20 с. При двух разных голосах по истечении: право решающего голоса чередуется между игроками от развилки к развилке; текущий решающий пилот обозначен заранее.
- Если голос дал только один — принять его после таймера. Если не голосовал никто — таймер не идёт.
- Отключение гостя не равно голосу: перейти в существующий сценарий восстановления/выхода, не продолжать опасный бой с потерянным напарником автоматически.
- Одиночная игра не имеет таймера выбора.
- Повторный пакет подтверждения не запускает переход повторно.

## 7. «Импульс» — награда за темп боя

### 7.1 Что получает игрок

После каждого успешно завершённого Combat/Elite/Boss — один бросок на **темпо-модуль**, общий для команды в коопе. Чем быстрее зачистка относительно эталона конкретной встречи, тем выше шанс. Обычные очки, ядра и магазинные награды не зависят от этого броска и не отнимаются.

Не делать бросок на каждого монстра: иначе спавнер слабых врагов становится фермой бафов, а союзники конкурируют за последний удар.

### 7.2 Счётчик времени

- Хранить `CombatActiveMilliseconds`, а не время с запуска приложения.
- Начало: угроза видима, закончилась `Arrival`, игроки могут наносить урон и основной бой начался.
- Считать всё обычное время боя: промахи, уклонения, кайтинг, замедления от правил и ожидание игрока учитываются.
- Не считать меню, стыковку, переход, согласованную паузу и обязательные заскриптованные интервалы, когда нет ни одной доступной для урона цели.
- Не останавливать счётчик из-за отсутствия попаданий, закрытия игроком обзора, нехватки элементального урона или добровольно затянутой механики брони.
- Если босс неуязвим, но его добавочные враги доступны, счётчик идёт.
- В Defense измерять темп всей пачки/встречи, а не искусственно заданный фиксированный интервал спавна. Пока нет модели эталона — темпо-бонус там выключен.
- В коопе время фиксирует хост; FPS клиента, VPN, фоновые меню гостя и локальное `Time.timeScale` не являются источником времени.

### 7.3 Формула первого тестируемого баланса

Эталон `Tref` хранится в профиле встречи по типу врага, бюджету угрозы и числу пилотов. Начальные ориентиры: Combat 30 с, Elite 45 с, Boss 75 с. Это только заглушки до измерения текущей игры; если реальные комнаты длятся 4 с, такие эталоны использовать нельзя.

Не пересчитывать Tref под каждый установленный баф игрока: улучшение не должно незаметно ужесточать норму. Профили solo/co-op калибровать отдельно, не делить время на два механически.

```text
ratio = combatActiveMilliseconds / referenceMilliseconds
quality = clamp01((1.0 - ratio) / 0.45)
chance = min(0.75, 0.15 + 0.40 * quality + 0.10 * consecutiveMisses)

если consecutiveMisses >= 2: награда гарантирована
иначе: награда, если детерминированный roll < chance
```

| Время боя, при Tref = 30 с | Шанс без предыдущих неудач |
| --- | --- |
| 16.5 с и быстрее | 55% |
| 23.25 с | 35% |
| 30 с и медленнее | 15% |
| Две предыдущие комнаты без модуля | Следующий допустимый бой: 100% |

- `consecutiveMisses` увеличивается только после завершённого допустимого боя без награды; сбрасывается после выдачи. Shop/Event/пропущенные комнаты/поражение не увеличивают его.
- В реализации использовать целочисленные миллисекунды и вероятность в basis points 0…10000 с зафиксированным округлением; таблицу выше покрыть тестами.
- Roll и предложения зависят от сохранённых `runSeed, nodeId, clearOrdinal, lootVersion`, а не от числа декоративных звёзд, музыки или количества вызовов UnityEngine.Random.
- Неудача не показывает гигантское «ПРОВАЛ». Коротко: «Модуль не найден · накоплен шанс». Успех: «Импульс: модуль найден».

### 7.4 Модули V0

Один выбранный модуль действует на **следующие два допустимых боя**, затем истекает. Текущий уже завершённый бой не расходует длительность. В коопе действует на обоих, независимо от того, кто нанёс последний урон.

| Модуль | Точный стартовый эффект | Видимый признак |
| --- | --- | --- |
| Форсаж затвора | +12% скорострельности: интервал делится на 1.12 | Короткий импульс у сопла и заметно чаще залп; без постоянной вспышки |
| Дальнобойная плазма | +18% скорости player projectiles; урон не меняется | Более быстрые снаряды, не менять рисунок пользовательского PNG |
| Резервный конденсатор | В начале каждого из двух боёв один временный блок входящего урона; расходуется после обычных звёзд-щитов | Отдельный маленький контур заряда, не поддельный четвёртый шарик |

- Максимум 2 активных темпо-модуля. Один тип не стакается: повторный выбор обновляет оставшиеся бои до 2, а не прибавляет ещё 2.
- При успехе показать 2 разных допустимых варианта из этих 3. Можно выбрать замену активного модуля или обновление; лимит не должен превращать успех в потерянный бросок.
- При заполненных слотах заранее указать, что заменяется. Никакой скрытой продажи/постоянной валюты.
- Кооп-выбор следует тому же механизму голосов/решающего пилота, но с отдельным `RewardChoiceId`. Награда не удваивается от двух подтверждений.
- Модули магазина остаются другой категорией: их существующие ранги и лимиты не изменяются. UI показывает магазинный ранг `2/4` и отдельно длительность темпо-модуля `ещё 2 боя`.
- Общий верхний предел скорострельности должен быть один в WeaponStatsResolver; стартовый технический минимум интервала 0.08 с подлежит проверке на высоких текущих фазах. Не вводить этот clamp в старый ranked classic без анализа существующей прогрессии.

### 7.5 Защита от снежного кома и эксплуатации

- Встречи должны проходиться без модулей. Не повышать скрытно HP врага при хорошем темпе.
- Нет дополнительного множителя score за темп в V1: только временный выбор. Сильный баф всё равно влияет на score, поэтому новый ruleset сначала без общего рейтинга.
- Не вознаграждать дружеские столкновения/самоповреждение для «поддержания комбо».
- Не сбрасывать таймер, pity или RNG при повторном входе, reconnect или восстановлении сохранения.
- Не начислять второй модуль при повторной доставке события смерти, повторном открытии карты или нажатии «продолжить».
- Быстрая смерть врага от объекта пространства считается полноценной победой: это желаемое emergent-взаимодействие, не исключение из бонуса.

## 8. Дополнительные идеи и их приоритет

### Включить в V1 через уже описанные правила

1. **Космический бильярд.** Линза → ядро → босс → обратка союзнику. Достаточно портала для ядра; отдельный скрипт «мемного события» не нужен.
2. **Предательский разряд.** Один заряжает узел снарядами, второй случайно ускоряет его сцепкой. Есть 0.9 с на реакцию; комедия не должна быть мгновенным невидимым уроном.
3. **Карманный отбойник.** Игрок поворачивает отражатель выстрелами, и атака босса возвращается. Панель не принадлежит одному игроку, оба влияют на неё.

### P2, только после плейтеста V1

| Идея | Почему интересна | Ограничитель |
| --- | --- | --- |
| Контрабандный груз на сцепке | Дотащить неудобный предмет до магазина; друг может случайно разогнать его | Опционально, награда заранее видна, потеря груза не заканчивает забег |
| Аварийный маяк | Вместо безопасного пути добровольно вызвать дополнительный бой ради выбора модуля | Только между боями и при подтверждении обоих; нет неожиданного спавна под UI |
| Проклятый магнит | Тянет ядра и лут, но также неприятные мины | Не в первой встрече; явное описание минуса; ограниченный радиус |
| Эхо маршрута | Раз в забег увидеть неизвестное правило следующего узла и переизбрать ещё не зафиксированный путь | Не возвращает награды и не повторяет уже пройденные комнаты |
| Дрон спасения | Выбывший пилот помогает толкать ядро | Сначала нужно изменить нынешнее общее HP команды; это отдельный проект, не маленький баф |

Не реализовывать все P2 автоматически. Сначала получить наблюдаемый плейтест: игроки сами используют хотя бы одно взаимодействие без подсказки разработчика.

## 9. Визуал, звук и интерфейс

### 9.1 Композиция и переход областей

- Пространство состоит из глубинных слоёв: далёкие мелкие точки → мягкая туманность → интерактивные объекты → корабли и атаки → HUD.
- Туманность не закрывает врагов и не имитирует телеграф атаки. Чистая боевая область важнее количества эффектов.
- Палитра региона — основа. Музыка добавляет ограниченный оттенок/энергию поверх неё; при смене трека регион не превращается в другой.
- Стартовая пропорция смешивания цвета: 70% профиль региона, до 30% музыкальный оттенок. Настраивать по скриншотам; яркость опасностей от музыки не зависит.
- На переходе смешивать два профиля и общие uniforms существующего процедурного шейдера, а не рендерить две дорогие полноэкранные камеры.
- Белые звёзды остаются декорацией; фиолетовые — существующими щитами. Новый объект не должен быть похож на собираемую звезду.
- Водяные кольца сохраняют текущую логику расширения до траектории. Смена региона не обрывает живой круг: цвет и прозрачность интерполируются до завершения его жизни.
- Не использовать `atan2` с непериодическим шумом/дробной частотой для замкнутых колец: ранее это давало видимый шов. Расширять текущие регрессионные тесты на все новые палитры.
- Вся смена пространства работает и при выключенной внешней музыке, без запроса разрешений на микрофон.

### 9.2 UI как редактируемые компоненты

Новые `RouteMapView`, `RewardChoiceView`, `RegionIntroView`, `SpaceRuleCodexView` — uGUI/TMP под существующим Canvas и Safe Area. Переиспользовать установленный шрифт с рабочей кириллицей, общую паузу и механизм переключения экранов.

- Gameplay публикует read-only модели. View не списывает награды и не переключает комнату напрямую; только отправляет команду в controller.
- Размещение хранится в prefab/сцене и редактируется без Play Mode. `OnEnable`/runtime не сбрасывает ручные RectTransform.
- Полная карта/выбор награды/магазин — модальные небоевые экраны. Открыт один, остальные скрыты; ввод движения не проходит сквозь модальное окно.
- В бою: компактные «область · комната» и существующая цепочка; информация о темпе может быть свёрнута в маленький индикатор, подробная формула — только в справке/результатах.
- Слева текущая комната, справа следующая, одинаковые размеры и baseline. Таймер смены траектории остаётся под соответствующей подписью, а не рядом случайным баннером.
- Представить полное экранное ограничение через общий `GameplayViewport`/safe combat bounds: камера вписывает ВСЮ траекторию с кораблём и щитами между занятыми областями HUD. Сначала найти существующий расчёт framing/zoom и расширить его, не создать независимую конкурирующую камеру.
- Положение/размер HUD не зависят от пользовательского world zoom. Спрятанная линия траектории не означает, что её границы можно перестать учитывать.
- Минимальная интерактивная область кнопки — целевой эквивалент 48 dp с проверкой на устройстве; 48 Canvas units не объявлять автоматически равными dp.
- Превью: portrait phone, landscape 16:9, tablet 4:3, длинный 20:9 экран, максимальная длина русского названия.

### 9.3 Объяснение механик

- Первый вход: название области, одна фраза «Линзы переносят ядро и снаряды» и простая пиктограмма; затем надпись уходит.
- Карточка узла до перехода: правило, риск, награда, название области.
- Справочник из паузы и меню: полноценное описание, что взаимодействует, что не взаимодействует, длительность предупреждения.
- После смерти: один главный источник последнего урона с пиктограммой, например «Разряд узла», а не сырой debug-log.
- Последние 8–16 структурированных событий урона хранить в debug-ring-buffer для воспроизведения; не выводить их пачкой поверх поля.

### 9.4 Аудио и доступность

- Звуки узла, линзы и награды идут отдельными pooled AudioSource/каналом SFX поверх музыки. Не менять musicSource.clip и не вызывать его Stop/Play от попаданий.
- Ограничение частоты SFX на объект/событие; синхронизированное событие не должно воспроизводить звук дважды у хоста.
- Профиль Reduced Motion уменьшает скачок, тряску, refraction и яркие полосы; не скрывает опасности, направление линз и их hitbox.
- Отдельные настройки: яркость атмосферы, интенсивность прыжка, тряска. Нельзя связывать читаемость атаки с общей прозрачностью музыкального визуала.
- Цветовые опасности обязательно дублируются формой/анимацией. Нет обязательных быстрых полноэкранных белых вспышек.

## 10. Архитектура реализации

### 10.1 Предлагаемые новые границы

Пути ниже — предлагаемая структура, не утверждение о наличии файлов. Не создавать абстракции без первого потребителя.

```text
Assets/Scripts/Run/
  RunState, EncounterState, RunPhaseController
  RouteProgression, RouteCommand, RunCheckpoint
Assets/Scripts/World/
  SpaceRegionDefinition, SpaceVisualProfile, SpaceRuleDefinition
  RegionPresentationController, SpaceObjectState, SpaceInteractionRules
Assets/Scripts/Rewards/
  TempoRewardRules, TempoRewardState, TempoModuleDefinition, WeaponStatsResolver
Assets/Scripts/UI/
  RouteMapModel/View, RewardChoiceModel/View, RegionIntroView, SpaceRuleCodexView
Assets/Settings/Space/      # ScriptableObject-данные; runtime читает без модификации assets
Assets/Tests/EditMode/     # чистые правила и генератор
Assets/Tests/PlayMode/     # фазы, UI, интеграция представления
```

Основной контракт: `input/command → общие правила → авторитетное RunState → read-only view models + VFX events`.

Новые маршруты и награды не реализовывать отдельно в локальной ветке GameManager и второй раз в CoopSimulationBridge. Оба должны вызывать один evaluator. Сетевой transport только доставляет команды/состояние, но не хранит вторую формулу наград.

### 10.2 Минимальный состав состояния

| Данные | Обязательные поля |
| --- | --- |
| RunIdentity | runId, runSeed, modeId, rulesetVersion, generatorVersion, lootVersion, contentHash, rankedEligible |
| RouteState | currentNodeId, visited/cleared IDs, available IDs, committedNextId, decisionSequence, resolvingPilot |
| EncounterState | encounterId, phase, phaseSequence, activeCombatMs, referenceMs, clearSequence, terminal outcome |
| RegionState | current/next visual and rule IDs, transitionStartTick, transitionDuration, object states |
| TempoState | consecutiveMisses, resolvedRewardIds, pending choice, active modules and remaining encounters |
| DamageEvent | sequence, tick, sourceId/type, target, damage, world position; без текстовых строк в hot path |

- Сериализовать стабильные IDs, не имена GameObject и не ссылки на ScriptableObject.
- Конфиги неизменяемы внутри забега. Изменение Inspector/runtime asset не меняет уже начатый ranked-compatible ruleset.
- PRNG имеет отдельные потоки/хеш-ключи для graph, encounters, rewards и visual. Не использовать глобальный `GetHashCode()` строки как стабильный межплатформенный seed; алгоритм PRNG/hash версионирован и покрыт known-answer тестами.
- Модификаторы оружия пересчитываются из базового набора, магазинных рангов и темпо-модулей. Не умножать текущую скорость каждый кадр и не откатывать делением при истечении бафа.
- Разряд/отражение/линза используют существующий путь проверки столкновений и применения урона; не вычитать HP напрямую в шейдере или UI.
- Ввести feature flags по компонентам: маршрут, биомы, tempo, интерактивные объекты. Выключение визуального флага не отключает телеграф игровых объектов.

### 10.3 Как входить в существующий код

1. `SectorGenerator`: добавить V2 рядом с legacy, новый validator directed graph и адаптер старого layout. Не ломать старый `Validate`, требующий двусторонних связей.
2. `AdvanceAuthoritativeRoom` и локальный `coopPreviewRoomIndex++`: заменить только для нового ruleset на общий `RouteProgression`; legacy оставить до паритетного теста.
3. `BuildExpeditionHudModel`: получать next/visited из RouteState. Больше не брать `Rooms[roomIndex + 1]` для нового режима.
4. `UpdateSpaceTravel` и музыкальные director/distortion: подписать на общий phase/region state. Удалить двойной запуск прыжка после миграции нового режима; legacy адаптер сохраняет прежнее поведение.
5. `ApplyExpeditionUpgrade`: сначала выделить чистые ограничения/результат применения шести магазинных модулей, сохранив их числа. Потом подключить кооп-команды; не смешивать их с темпо-модулями.
6. `GameplayRulesValidator`: оставить существующие проверки и добавить новые suites; GraphicsRegression расширить новыми профилями, не заменять before/after fixture.

## 11. Сеть, восстановление и честность результатов

### 11.1 Авторитет

- Текущая модель — клиент-хост. Хост решает route, combat time, объектные контакты, смерть и награду; Relay не становится игровым сервером от добавления карты.
- Клиент присылает только намерение: vote/confirm/reward choice с монотонным command ID. Проверяются отправитель, текущая фаза, допустимые IDs, последовательность и лимит частоты.
- Непрерывные положения объектов — в bounded snapshot; дискретные clear/reward/route commit — доставка с подтверждением или восстановлением из последующего полного состояния. Не полагаться только на одноразовый ненадёжный VFX event.
- Не отправлять туманность, звёзды, каждую частицу или амплитуду личной музыки по сети. Регион определяется ID; локальная анимация может отличаться, правила — нет.
- Новый snapshot/handshake обязательно версионировать. Несовместимому клиенту показывать «Обновите игру», не читать неизвестный пакет как старый.
- Late join/reconnect получает текущую фазу, принятый маршрут, объекты, время, pending reward, выбранные модули и их срок, pity. Не запускает повторное прибытие/награду.
- Host migration не добавлять в этом ТЗ. При потере хоста — понятное завершение/восстановление согласно реально доступному существующему механизму, без выдуманного автоматического продолжения.

### 11.2 Сохранение и идемпотентность

- Checkpoint после фиксации clear ДО показа награды; после выбора награды; после route commit; после завершения/провала.
- `rewardId = runId + encounterId + clearSequence + lootVersion`. Записывать не только последний ID, а набор применённых ID внутри забега: повтор более старого пакета тоже не должен сработать.
- Сохранять outcome броска и варианты выбора, а не бросать RNG снова после reload.
- Локальная запись атомарная: временный файл → проверка → замена предыдущего с recoverable backup. Схема versioned; повреждение не должно молча выдавать награду ещё раз.
- Если процесс закрылся посреди боя, V0 разрешает восстановление только с начала checkpoint комнаты без начисления незавершённой награды. Уже зафиксированные награды/маршрут не откатываются; RNG комнаты сохраняется. Такие восстановленные экспериментальные забеги остаются без рейтинга.
- Не обещать честный онлайн-рейтинг на основании client hash. Хост на телефоне и локальное сохранение не являются доверенным античит-сервером.

### 11.3 Рейтинг/Firebase

- V0/V1 beta нового режима явно marked unranked в меню и результатах, не отправляет score/MMR в существующую общую таблицу и не меняет локальный текущий MMR. Старые режимы работают как раньше.
- Можно хранить отдельный локальный рекорд нового ruleset. Не создавать/публиковать новую облачную коллекцию в рамках первого игрового среза.
- Для ranked rollout нужен отдельный checkpoint решения: режим/версия результата, раздельные лидерборды или согласованная нормализация, доверенная серверная валидация/дедупликация и проверка Firestore Rules. Не менять существующую формулу MmrSettings и не сбрасывать игрокам рейтинг «для удобства».
- Миграция существующих checkpoint: старые seed/version завершаются legacy-кодом или предлагается явно начать новый экспериментальный забег; не интерпретировать старый индекс как новый nodeId.

## 13. Проверка и критерии приёмки

### 13.1 EditMode / чистые правила

- Минимум 1000 seed: воспроизводимость, не более 24 узлов, достижимость выхода, отсутствие циклов, валидные IDs, путь через финального босса и гарантированный сервис.
- Known-answer fixtures по seed и versions; изменение порядка визуальных RNG-вызовов не меняет маршрут/лут.
- Только соседний доступный узел может быть выбран; неподходящий command/phase/replay отвергается.
- Формула tempo монотонна по времени; значения из таблицы совпадают; после двух misses третий бой гарантирован; небоевые комнаты не влияют.
- Пауза, forced invulnerability и shop не накручивают время; добровольное ожидание/кайтинг его не останавливают.
- Срок модулей ровно два следующих боя; повтор обновляет до 2; максимум два типа; stat resolver не накапливает погрешность от применения/снятия.
- Duplicate clear/choice/reconnect не увеличивает ранги и не повторяет награду.
- Порталы сохраняют скорость/элемент/TTL; лимит проходов и cooldown ядра соблюдается; нет бесконечного цикла двух линз.
- Разряд не заряжает себя, максимум один урон от одного event; отражатель не выдаёт повторного score за рикошет.
- Валидность размещения объектов на круге, овале, повёрнутой восьмёрке, квадрате и промежуточных morph-состояниях.

### 13.2 PlayMode / интеграция

- Пройти Start→Combat→Reward→RouteChoice→Departing→Arrival→Shop→Boss→Completed и отдельный сценарий Failed.
- Во всех небоевых фазах не теряется HP; враги не умирают до появления; атаки очищаются на clear.
- Выбор альтернативы реально меняет следующую комнату, не только её текст/цвет.
- Мир меняет масштаб через пользовательский zoom, UI остаётся прежним; верх/низ/бока всей траектории видимы.
- Нет нового `OnGUI` для карты/награды; можно вручную передвинуть их Canvas-элементы вне Play и изменение сохраняется.
- Пауза единая, без кнопки выхода под пальцем; модальные окна не пропускают нажатия на движение.
- Магазин стыкуется до появления карточек; описания, rank/max, реально применённые параметры соответствуют друг другу.
- Новые SFX играют поверх музыки, не перезапускают её и не создают повторный резкий тик от дублированных событий.

### 13.3 Графика и Android

- Сохранить парные скриншоты/короткие записи до/после: 720×1280, 1280×720, 1080×2400, 1600×1200; safe-area inset, длинная кириллица, крайние zoom.
- Проверить кольцевые швы на всех профилях в D3D11 и доступном Android graphics backend, без NaN/чёрного кадра в `OnRenderImage`.
- Unity-тест отдельного шейдера полезен, но не заменяет gameplay capture со звёздами, врагами, HUD и переходом камеры.
- Испытать внешнюю музыку в наушниках, встроенную музыку, отсутствие сигнала и отказ в разрешении. Регион и игровые правила работают во всех случаях.
- Физический Android 9 и второй Android/планшет — обязательны для заявления о device-ready; эмулятор является дополнительным, а не заменяющим тестом.
- 20 минут игры/повторных переходов: отсутствие монотонного роста памяти, утечки материалов/RenderTexture/AudioClip и деградации кадра после 10 рестартов.

### 13.4 Сеть

- Два реальных клиента: создание/вход, разные голоса, истечение таймера, единый выбор награды, два последовательных перехода и финал.
- Профили проверки: нормальная сеть; RTT примерно 150 мс; RTT 300 мс с jitter 50 мс и 2% loss. Указать реальные средства и измерения, не объявлять VPN точным эмулятором этих значений.
- Reconnect во время боя, pending reward, route vote, прыжка и после clear. На обоих одинаковые HP/модули/узел/награда.
- Дублированные и переставленные команды, устаревший snapshot, несоответствие content/protocol version.
- Гость не может подделать время, NodeId, clear или rewardId для получения усиления.
- Хост потерян: понятный безопасный сценарий, отсутствие двойного результата, никакого обещанного host migration, которого нет.

### 13.5 Бюджет производительности

Это release targets относительно baseline M0; если baseline уже медленный, измерять абсолютный и добавленный расход отдельно.

- Новый steady-state gameplay-код: 0 B GC Alloc/frame; UI перестраивается по изменениям модели, не каждый кадр.
- Пулы для объектов и VFX; отсутствие Instantiate/Destroy на каждый снаряд/разряд.
- Стартовый лимит: 1 интерактивный объект/пара линз, 32 одновременные частицы попадания на объект, не более 96 новых частиц этих механик на экран. Не уменьшать чужие существующие эффекты без измерения.
- Цель добавленной стоимости: до 1 мс CPU симуляции и до 2 мс GPU атмосферы на выбранном целевом устройстве, измерять profiler/Frame Debugger. Числа не считать подтверждёнными до профилирования.
- Цель кадра: устойчивые 60 FPS на основном устройстве; low quality для старого Android — устойчивые 30 FPS. 95-й percentile frame time не хуже выбранного бюджета; отдельно показать worst spikes перехода.
- Low tier уменьшает декоративный шум/частицы/refraction, но сохраняет все интерактивные объекты и телеграфы.
- Дополнительный обычный сетевой трафик целевой до 1 KB/s на клиента сверх baseline; события/initial snapshot отдельно. Если формат не укладывается, показать измерение, а не скрыто снизить существующую частоту синхронизации.

## 14. Телеметрия и критерии «стало лучше»

Сначала локальный структурированный отчёт, без записи личной музыки, микрофона, аккаунтов или новых отправок в облако. Подключение внешней аналитики — отдельное решение.

События: `region_entered`, `route_offered/committed`, `wormhole_taken`, `encounter_started/cleared/failed`, `tempo_roll`, `module_chosen/expired`, `space_object_interaction`, `damage_received`, `run_completed`.

Поля: runId, seed, mode/ruleset, encounter/node ID, playerCount, activeCombatMs, referenceMs, chanceBp, pity, module ID, space rule ID, source damage type, quality tier. Debug seed можно копировать из паузы/результата; не возвращать раздражавшие пользователя seed-баннеры поверх поля.

Проверять на плейтесте:

- После первой области игрок своими словами объясняет её правило и хотя бы раз намеренно использует объект.
- Перед выбором игрок различает безопасный и рискованный маршрут, а не жмёт случайную одинаковую иконку.
- После смерти игрок называет источник урона; отчёт повреждений это подтверждает.
- Медианное время боя и распределение `T/Tref` не дают всем постоянные 55% или всем постоянные 15%. Иначе сначала чинить эталоны.
- У игроков без темпо-модуля остаётся реалистичная вероятность пройти бой; серия удач не превращает босса в мгновенное исчезновение.
- Сравнить завершения забега/длительность/ущерб между ветками и регионами. Не балансировать по одному идеальному прохождению разработчика.
- Для первичного UX gate: минимум 5 полных solo-забегов и 3 совместных сессии, затем список наблюдаемых проблем. Это поиск дефектов, не статистическое доказательство удержания.

## 15. Главные риски и принятые решения

| Риск | Принятое решение |
| --- | --- |
| Красивая карта, но комнаты всё равно идут по индексу | Сначала общий RouteProgression и новые validators, затем UI |
| Бафы усугубляют разницу сильного и слабого игрока | Временность, 2 слота, pity, нет потери базовой награды |
| Магазин работает в solo, но расходится в коопе | Общие upgrade rules и отдельный M7; не выдавать старый UI за сетевую поддержку |
| Музыкальные эффекты маскируют урон | Отдельный визуальный язык/канал телеграфов, Reduced Motion не скрывает hitbox |
| Новый баланс ломает общий MMR | Экспериментальный unranked ruleset и отдельный ranked gate |
| Сохранение позволяет перебрасывать лут | Зафиксированные outcome/варианты/IDs до показа UI |
| Портал создаёт мгновенный удар из-за спины | Безопасное размещение, ограниченный список объектов и задержка реакции |
| Поломать уже настроенный вид ради нового визуала | Сохранить пользовательские значения, V2-профили отдельно, сравнение до/после |

**Definition of Done V1:** воспроизводимый маршрут с реальным выбором, понятные три пространства, видимые взаимодействия, честная командная темпо-награда, отсутствие скрытого урона и перекрытия поля, одинаковые authoritative результаты на двух устройствах, сохранённый legacy и подтверждённый performance budget либо явно согласованное отклонение.
